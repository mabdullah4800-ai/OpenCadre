# Launch client gate

**Decided 2026-09-19 by the operator, revised the same day:** OpenCadre launches when the **Tier 1** tools below are
fully working. Fewer tools that work end to end beat more that half-work: every tool on the site is a promise. The
rest follow as updates after launch. This page defines "fully working", records where each tool stands on `main`,
and assigns the work. It is the plan the fleet builds against. Update it in the same PR that changes a cell.

## 1. What "fully working" means

A tool passes the gate when all six hold **on a real install**, measured and written down in its
`docs/design/HARNESS-<TOOL>.md`:

| # | Capability | The bar |
|---|---|---|
| 1 | **Connect** | One command (`opencadre connect`) detects the tool and writes its config |
| 2 | **Identity** | Every chat is its own agent on the roster. Two chats on one machine are two agents, never one |
| 3 | **Mail** | The agent learns about new mail without the human asking: woken when idle where the vendor allows it, otherwise at its next turn |
| 4 | **Clearance** | A risky command is held **before** it runs, not reported after, until someone other than the requester decides: a person, or another agent (operator ruling 2026-09-23, decision #30875). *Since 2026-09-30 (migration 53) the hub lets only a signed-in person decide a clearance; an agent's decide is refused.* |
| 5 | **Lapsed bill** | When the workspace stops paying, the tool keeps working as a plain tool: hooks and proxy go quiet, never block |
| 6 | **Verified** | A smoke run on a real install is recorded (command, output, date), and `opencadre doctor --client <tool>` reproduces it. **A smoke run that cannot fail is not a smoke run:** name the input that would make it fail |

`doctor` is not a seventh capability. It is the instrument that reports capabilities 1–5 for one tool on one machine, which is why it is built first (§3) and why capability 6 depends on it.

**What makes a measurement count — the bar applies to EVERY assertion behind a cell, not only to the smoke run.**

> **A `doctor` exit 0 is WIRING, not PROOF.** And more generally: **for every assertion behind a green
> cell, name the world in which it returns something else.** If you cannot name one, the assertion is
> decorative, and the cell it supports is not evidence.

This is not a style rule; it is the one that catches the failures this table has actually shipped. Two
worked examples, both real, both found after the cell was already green:

- **`count >= 0` is true for every array, including an empty one.** A `receive` leg asserting that
  passed while *nothing had arrived* — it checked the response's SHAPE, not that delivery OCCURRED.
  The falsifier exists and nobody had named it: `count >= 1`. See `HARNESS-CLAUDE-CODE.md` §10.1.
- **A `doctor` exit 0 proves a config parses and a credential resolves.** It does not prove a chat
  was briefed, a wake fired, or a command was blocked — so a cell whose only backing is a doctor
  green is a wiring claim wearing an evidence label.

**A measurement whose negative cannot be stated is a claim about the instrument, not about the tool.**
Where that is the case, the cell says so — the same discipline as naming a vendor limit, and the same
reason a not-measured state is kept distinct from a pass.

**When a measurement is still current (adopted 2026-09-30).** Every cell's evidence is keyed by **(hub build, client
version, the client files the leg runs through)**. A re-run is owed only when one of those changes **on the leg's own
path**. For the client files, that means the import closure of the leg's entry helper. A file-level byte check is
conservative: a changed file in the closure is flagged, then cleared or not at function level, and the harness doc
records which. The first leg-to-files map is in HARNESS-CLAUDE-CODE.md §10.4. Each piece of evidence also names its
instrument (for example *real GUI*, *app binary*, *emulated desktop entrypoint*), and an emulation never stands alone
for a GUI cell. A file check clears only **our** side of a change. When the vendor's client or host changed, or its
earlier version was not recorded, the cell is **owed** until it is measured at that version or impact-cleared with
evidence about that host.

Where the vendor makes one of these impossible, the harness doc must name the limit, and the gate is the best the
vendor allows, stated on the site. It must never be claimed as full.

## 2. The tiers

### Identity and closed-chat mail advisory (2026-10-07; source-bound)

The integrations page and computer-connect output no longer promise that every Codex app restart assigns a new
name. `scripts/opencadre-mcp.mjs` selects a chat channel from a verified per-call stamp; its unstamped process
fallback instead generates a fresh id per process (`scripts/opencadre-config.mjs`, `resolveSessionId`). A matching
chat-proven seat can resolve or revive the same hub agent (`src/devices.ts`), subject to project/device access,
removed-agent checks and the applicable billing/session/plan limits. A new identity does not inherit that agent's
name or inbox: `src/service.ts`, `getMessages`, selects unread mail for the authenticated recipient identity.

Closed chats are not woken. A resumed chat can check that identity's unread mail only if it returns with the same
identity and access permits. `tests/sessions.test.ts` covers matching-seat revival and separate-agent inboxes;
`tests/codex-session-stamp.test.ts` covers verified stamp selection and ambiguous-stamp refusal. Those source and
synthetic controls do **not** establish a real app restart followed by reading old queued mail. That end-to-end
measurement remains owed; no historical capability cell below is changed or upgraded by this advisory.
